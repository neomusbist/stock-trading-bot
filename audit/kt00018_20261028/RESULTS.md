## 전용 제한과 오류 처리

- kt00018만 같은 Windows 사용자·앱키·서버 기준의 공통 파일/OS 잠금을 쓴다. Rest 인스턴스나 인증 세션을 새로 만들고 토큰을 갱신해도 제한을 초기화하지 않는다. 다른 PC/별도 외부 프로그램의 호출까지 제어한다고 주장하지 않는다.
- 실제 HTTP 처리가 끝난 뒤 0.55초의 quiet interval을 둬 어느 1초 구간에서도 최대 2회로 제한한다. 모의투자 서버는 공식 일반 정책을 고려해 1.05초다. 요청 슬롯을 미리 여러 개 예약한 후 한꺼번에 보내지 않는다.
- 전용 잠금을 기다리는 동안 기존 전체 TR rate_lock을 점유하지 않는다. 주문·다른 조회 TR에는 새 전용 잠금을 적용하지 않는다. 기존 0.3초 공통 제한은 보존했다.
- 연속조회 페이지, 인증 재시도, 네트워크 재시도도 매 HTTP 시도마다 같은 전용 장치를 지난다. 진단 요청은 미래 슬롯을 선점하지 않고 양보한다.
- HTTP 429 및 return_code 1700/429 등 명시적 유량 응답은 최대 총 3회 시도한다. 1초·2초 백오프를 공유 상태에 반영하고 Retry-After를 우선한다. 오래 기다리라는 응답이면 워커를 장시간 붙잡아 반복 전송하지 않고 공유 cooldown을 남긴 뒤 오류로 반환한다. 주문은 계속 자동 재전송하지 않는다.
- JSON 오류·권한 오류·잠금/저장 실패는 빈 잔고로 바꾸지 않는다. 비정상 종료의 inflight 표식은 다음 요청 전에 최소 1.05초를 추가 대기한다. 잘못된 제한 상태 파일은 전송을 막는다. 제한 캐시에는 토큰·앱키·계좌·잔고를 기록하지 않는다.
- 계좌 전용 워커에서 유량 오류가 나도 별도 ka10075 미체결 조회를 계속하며 이미 받은 체결 조회 결과를 오류의 별도 영역에 보존한다. 부분 결과를 holdings/cash가 있는 정상 계좌 스냅샷으로 만들거나 금융 장부에 전체 대조 완료로 적용하지 않는다. 기존 WebSocket 주문/체결 수신도 중단하지 않는다.

## 신규매수 차단과 보유 보호의 분리

명시적 kt00018 유량/로컬 제한 오류에서는 balance_refresh_uncertain을 세운다. 신규매수와 신규 진입 수량의 자본 신선도 심사는 실패한다. 현금·보유·마지막 정상 계좌 시각을 0이나 현재 시각으로 바꾸지 않는다.

마지막 정상 대조가 아직 기존 15초 유효기간 안에 있을 때에만 기존 보유 보호를 계속할 수 있게 한다. 15초를 연장하지 않으며, 이미 오래됐거나 불명확한 계좌에는 보호 주문 권한도 새로 부여하지 않는다. 비유량 오류의 기존 fail-closed 동작도 보존했다. 오류가 지속돼 기존 신선도 경계를 넘으면 실제 수량을 새로 확인할 수 없다는 제한은 남는다. 성공한 전체 계좌 대조 이후에만 uncertainty를 해제한다.

이는 임의의 손절·위험 한도 완화가 아니다. 일시적 조회 제한을 즉시 전체 보유 보호 중단으로 바꾸지 않고, 기존 확인 정보의 원래 유효시간만 사용하는 변경이다. 수동 보유 HARD_LOCK·영속 주문 의도·중복 주문·연속손실 제한·자본·위험 설정을 변경하지 않았다.
