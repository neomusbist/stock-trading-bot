# 보호청산 안전성 및 PAPER 관측 준비

## 결과

기준 커밋 `0f2abe78b87935b32ae21b11c44274bd6c155775`의 C2/관측 감사는 재사용했다. C2·A/B/C 전략, RR·위험예산·자본·WATCH 구독은 변경하지 않았다. 새 전략은 없다.

**계좌 조회만 오래된 경우의 보호 전용 권한을 구현했다.** 현재 프로세스에서 검증한 완전한 계좌 기준점, 그 이후 체결 원장, 5초 이내의 완전한 체결·미체결 조회 및 신선한 실행 가능 호가가 모두 필요하다. 신규매수의 계좌 신선도 기준은 그대로다. 수량/주문/호가를 증명할 수 없으면 매도하지 않고 영속 보호 실패 및 GUI 긴급 상태를 제공한다.

LIVE는 기존 `R6-KT00018-20261028-7d3c3d949105`로 유지했다. 새 후보 `R6-PROTECT-OBS-20261029-239d14a4fd41`는 설치하지 않았다.

## 원인과 수정

기존에는 AccountWorker가 일부 계좌 오류 후 독립 미체결 조회를 해도 결과를 보호청산 판단에 사용하지 않았다. 정상 체결 후에는 활성 주문이 없다는 이유로 체결 조회 힌트가 꺼지기도 했다. core의 청산 루프와 최종 주문 가드 모두 계좌 15초 제한만 사용했다.

- `automation/protection_safety.py`: 현재 프로세스의 계좌 기준점과 체결 변화량으로 보유수량을 대조한다. restart/disconnect/session 변경은 새 계좌 기준점을 요구한다. 이전 프로세스의 저장 수량만으로 권한을 복구하지 않는다.
- `automation/runner.py`: 봇 보유 중에는 체결 조회를 유지하고, 계좌 조회 실패 시 성공한 완전한 체결 조회와 독립 미체결 조회를 전달한다. 부분 조회를 잔고·현금 0원으로 reconcile하지 않는다. 조회 시각과 monotonic 만료를 함께 검증한다.
- `core/engine.py`, `automation/engine.py`: 일반 매수 권한과 보호 매도 권한을 분리했다. 영속된 청산 요청, 소유권, 수량, 예약 주문을 최종 전송 직전 다시 확인한다. financial INTENT/체결/보호 상태의 fsync는 유지한다.
- `automation/position_health.py`: 체결이 없는 정상 구간에도 실제 0D의 잔량과 수신 시계를 보존한다. 호가를 가짜 체결로 만들지 않는다.
- `operator_service.py`, `operator_ui_service.py`: 진단 로그가 없어도 영속 원장의 보호 실패를 화면의 긴급 상태와 상세 사유로 표시한다.
- 관측 기록은 보호 전용 허가와 계좌 불확실성 차단을 구분한다. best-effort 기록기 예외가 보호 주문을 취소하거나 원장 권한을 만들지 않는다.

## 장애별 동작

| 상황 | 수정 후 동작 |
|---|---|
| 매수 체결 후 잔고 조회만 15초 이상 실패 | 완전한 최근 주문상태 + 기준점/체결 원장 + 신선한 호가가 일치하면 검증된 잔량의 보호 매도 허용. 신규매수 금지 |
| 일부 수량이 매도 주문 중 | 미체결 잔량 예약, 같은 종목의 추가 SELL 금지. 먼저 체결·취소를 확정한 뒤 남은 수량만 순차 처리 |
| 매도 결과 UNKNOWN/취소 결과 불명 | 재전송 금지. 청산 요청과 불명확 상태 보존, 긴급 알림, 완전 대조 요구 |
| 계좌·미체결/체결 조회 동시 실패 | 보호 매도 권한 생성 금지. 현금·보유를 0으로 만들지 않고 실패를 영속 기록 |
| 로컬 취소/거절인데 서버 미체결 잔량 존재 | 수량 신원 충돌로 기준점 무효화. 이후 빈 미체결 응답만으로 복구하지 않고 계좌까지 다시 대조 |
| 다른 종목과 주문번호 충돌/로컬 중복 주문번호 | 권한 생성 금지 및 전체 재대조 |
| 재접속·프로세스 재시작 | 새 완전 계좌 대조 전 보호 fallback 금지. 기존 청산 의도는 보존 |
| 오래된 호가/잔량 불명/재고 잠금/HARD_LOCK | fallback 금지. 신선도 제한이나 HARD_LOCK을 우회하지 않음 |
| 진단 기록기 예외·대기열 포화 | 금융 원장·주문 경로와 분리. 기록 누락은 UNKNOWN |
| 금융 원장 체크포인트 실패 | 전송 금지. 진단 실패와 다르게 처리 |

확인된 pending SELL은 한 종목당 하나씩 순차 처리한다. 부분 주문만 걸려 남은 수량을 보호할 수 없으면 남은 수량도 긴급 상태에 표시한다. 주문 접수는 체결 보장이 아니며, 가격 갭·유동성 부족·거절·미체결 위험은 남는다.

## 회귀 및 통합 검증

- 동일 양성 시험을 종전 설치 소스+관측 복제본에서 실행해 **FAIL(보호 SELL 0)**을 재현했다. 수정본에서는 **PASS**다.
- 개발 관련 **260 PASS**. 기존 전략·수량·원장·손절·API 제한·관측 및 GUI 서비스 포함, 저장소 전체 전수검사는 아니다.
- 실제 설치 소스+실제 설정 복제본 **46 PASS**. 새 보호 장애 시험과 KT00018/인증 시험을 실제 native 경로로 실행했다.
- 모의 설치·롤백 **11 PASS**. 실제 LIVE 적용은 아니다.
- 복제본에서도 broker 전송 전에 정확한 영속 INTENT를 확인했고 네트워크 연결은 차단했다. 합성 주문/체결은 실계좌 성공이나 수익 증거가 아니다.
- API `core/broker.py`, `core/balance_rate.py` 및 native 전략/비용/정책/청산 소스 해시를 보존했다. 후보는 예전 관측 6파일에 안전성/GUI 5파일을 더한 정확히 11파일이다.

설치본의 새 후보 파일 외 함수는 AST로 비교했고, LIVE의 선언 소스 103개와 보호 6파일은 작업 전 해시와 같다. 후보의 선언 소스는 신설 모듈 2개를 포함해 105개다.

## 사전 등록 보호주문 확인

[키움증권 공식 SDK 스펙](https://github.com/Kiwoom-Securities/Kiwoom-REST-API/blob/main/kiwoom/_data/kiwoom_api_spec.json)의 `kt10001` 요청 종류에는 **28: 스톱지정가**가 있으며 조건단가 `cond_uv`가 있다. [공식 4991 안내](https://download.kiwoom.com/hero4_help_new/4991.htm)는 거래소가 스톱 조건을 감시하고, 도달 후 지정가 주문으로 참여한다고 설명한다.

문서상 지원과 현재 계좌에서의 실제 접수·조건가격 해석·거래소 허용 여부·체결 보장은 다르다. 현재 프로젝트의 Rest.submit은 스톱 주문 등록/원장 수명주기/OCO를 구현하지 않는다. 이번 작업에서 스톱 주문을 새로 등록하거나 활성화하지 않았다. 별도 설계·승인 없이 기존 보호 SELL과 병행하면 이중 주문 위험이 있다.

## 실제 PAPER 검증 준비

기존 `observe_paper`/`c2_paper`와 기록기를 재사용했다. 새 `research/paper_funnel.py`는 WATCH 고유 종목, 구조 ID, 독립 구조 검증, 경제성·트리거, 원본이 보고한 게이트와 실제 엔진이 검증해 접수한 PAPER 주문, 체결·청산 및 비용 후 추정 순손익을 분리한다.

수신 시각·계좌·호가 연결이 없는 원본 PASS 표시를 주문 적격으로 승격하지 않는다. capture_session과 종목을 구조 키에 포함한다. 원본 native 상세 기록이 없으면 해당 단계는 UNKNOWN이며, 반복 평가를 독립 기회 수로 합산하지 않는다. 공유 기록기의 시작 손실 카운터와 관측 중 증가량을 따로 표시하고 증권사 패킷 유실 수는 UNKNOWN으로 둔다.

이번 작업에서 새 실제 장의 PAPER 관측은 시작하지 않았다. 실제 WATCH/경제성/주문 적격/순손익은 아직 UNKNOWN이다. 기존 개발 날짜의 C2 자료를 다시 수익성 검증한 것으로 보고하지 않는다.

## 남은 위험

- 완전한 주문상태 조회까지 불가능하면 소프트웨어가 안전한 보호 매도를 보장할 수 없다. 긴급 알림 후 증권사 채널 확인과 복구 대조가 필요하다.
- 체결 원장 밖의 관측 불가능한 수량 이전·외부 수동 동작까지 보장하지 않는다. 발견된 외부 주문·수량 충돌은 전체 재대조로 막는다. BOT 종목의 수동 혼용은 피해야 한다.
- 보유 중 읽기 전용 체결 조회가 추가된다. 워커에서 수행하며 KT00018 제한은 그대로지만, 실제 PC·장중 부하 및 증권사 거절 조건은 통제 적용 이후 확인해야 한다.
- 실제 실시장 PAPER 적격 신호·기대값·실계좌 보호 체결은 아직 입증되지 않았다.
